## 2. IEEE-CIS Feature-Availability Ledger (Section 7.2 & P1-8 Decision)

Because the IEEE-CIS competition dataset contains masked and derived feature blocks whose exact real-time computation latency is not fully disclosed by Vesta Corporation ([IEEE-CIS, 2019](https://www.kaggle.com/c/ieee-fraud-detection)), every column family must be classified by its plausible availability at transaction authorization:

| Feature Family | Columns | Count | Data Type | Missingness Profile (Literature Verified) | Plausible Availability Tier | Graph / Modeling Role & Audit Rule |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Transaction Key & Time** | `TransactionID`, `TransactionDT` | 2 | `int64` | $0.0\%$ missing | **Tier 1: Authorization-Time Exact** | Primary join key and monotonic temporal ordering axis. Never used as a raw numeric split feature to avoid tree memorization of time windows. |
| **Transaction Amount & Product** | `TransactionAmt`, `ProductCD` | 2 | `float64`, `category` | $0.0\%$ missing | **Tier 1: Authorization-Time Exact** | Core transaction attributes ($\ln(1 + 	ext{TransactionAmt})$, product category). `ProductCD` has only 5 categories (`W, H, C, S, R`) and must **never** be used as a graph entity relation (would create a massive uninformative hub). |
| **Card Proxy Attributes** | `card1`–`card6` | 6 | `int64`, `float64`, `category` | $0.0\%$ (`card1`) to $1.5\%$ (`card2`–`card6`) | **Tier 1: Authorization-Time Exact** | `card1` ($\sim 13,553$ unique values in train) and composite `card1_card2_card3_card5_addr1` serve as primary **Card Proxy** entity keys (`Relation R1`).
